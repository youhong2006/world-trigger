# 可自由探索 BORDER 總部：3D 場景設計與實作規格

> 狀態：設計提案，尚未實作。以下 B2–6F 全為 **C 級遊戲原創配置**，不是官方樓層表。請參照 README.md / layout.md / references.md 的 A/B/C 證據分級。

## 目標
從既有三門市 Three.js 場景步行進入 BORDER 總部，保持第三人稱/第一人稱、碰撞、移動、戰鬥與設定功能。室內可探索、可透過樓梯及電梯移動、可進出各小隊房間、訓練室與指揮中心；外部城市不得被替換。

| 樓層 | 分區 | 遊玩內容 |
|---|---|---|
| B2 | 後勤／機庫 | 遠征艇機庫與物流預留，部分區域可管制 |
| B1 | 技術研發 | Trigger 研發、維修與機房 |

## 建築導覽動線
城市道路 -> BORDER 主入口 -> 1F 大廳 -> 主電梯／實體樓梯 -> 2–3F 訓練大廳 -> 編號訓練室 -> 虛擬戰鬥場景。
大廳 -> 電梯／樓梯 -> 4–5F 小隊走廊 -> 對應小隊自動門 -> 可進入的小隊作戰室。
大廳 -> 電梯／樓梯 -> 6F 指揮中心 -> 門禁 -> 指揮室。
後勤動線 B1/B2 應避免穿越訓練大廳。

## 核心場景元件
- HeadquartersInterior：總部室內主場景，具 floorId、區域 bounds、樓層資料與分區載入。
- FloorRegistry：樓層、入口點、電梯出口、樓梯連接、門與房間索引。
- SlidingDoubleDoor：電動雙扇橫向滑動門，CLOSED/OPENING/OPEN/CLOSING/LOCKED 狀態、感應/互動、0.6–1.0 秒動畫、防夾與碰撞。
- Elevator：轎廂、內外呼叫面板、樓層選擇、關門/移動/開門狀態，玩家與攝影機安全遷移；視效可採隱藏式樓層切換以降低渲染負擔，但玩家操作流程連續。
- Stairwell：實體可步行樓梯與扶手，與角色碰撞相容；不可僅以按鍵傳送。
- SquadRoom：資料驅動的小隊專屬房間，teamId、隊名、隊徽、門禁、座位、戰術螢幕、裝備展示；房間位置為 C。
- TrainingRoom：編號門、訓練入口與離開出口；戰鬥模擬場景單獨載入，非實體大樓內的等比例城市。
- CommandCenter：大型螢幕、指揮席、監控設備與門禁；細節為 C。
- Wayfinding：樓層指示牌、電梯 UI、門牌、玩家當前區域提示；無障礙/緊急疏散路線預留。

## 尺寸與比例
保持既有世界單位（公尺）、角色約 1.75m、既有城市碰撞。走廊 2.5–4m、電動門 2.0–2.8m 寬與 2.2–2.6m 高、樓層高 3.5–4.5m、訓練中庭挑高 8–15m，皆為 C 級建模初始值。尺寸以人物視角及截圖比例再校正。

## 技術要求（Three.js / Vite）
1. 先檢查現有城市模型、入口座標、玩家控制器、碰撞與鏡頭；不重構不相關系統。
2. 室內幾何與城市分區管理，僅渲染可見樓層／房間；可採按區域延遲載入與遮擋剔除。
3. 電梯需有實際選層與動畫狀態，防止切換樓層後玩家穿模或掉落。
4. 門開關時同步更新碰撞，並避免 NPC/玩家被夾住。
5. 房間資料驅動，不要硬編碼全部小隊房間的世界座標。
6. 指揮中心、訓練區、隊伍區要有不同視覺語言，但以白灰金屬與藍色燈條保持一致。
7. 先完成 1F + 2–3F 灰盒、電梯與樓梯，再擴充 4–6F、B1/B2。
8. 保留原有遊戲功能、現有按鍵、手機/桌面效能要求及 GitHub Pages 路徑；執行 npm test 和 npm run build。

## 驗收條件
- 玩家可從城市走入總部，再走出返回原處，位置與控制正常。
- 玩家可實際走樓梯抵達相鄰樓層；電梯可選層並安全抵達。
- 至少一個可進入的小隊房、一間訓練室及指揮中心具可走動室內。
- 自動雙開門有動畫、碰撞與防夾。
- 訓練模擬場景與物理總部清楚分離。
- 無穿牆、掉落、鏡頭卡牆、反覆觸發門、樓層切換錯位。
- 原有城市、戰鬥、設定及測試保持正常。
- 明確標示已完成、尚未完成與 A/B/C 資料來源。
